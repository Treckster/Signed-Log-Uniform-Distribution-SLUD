## Q1. Fixed-target vs fixed-budget, ERT/aRT and censored (failed) runs, runtime ECDFs (COCO / IOHanalyzer)

### Takeaway
The current headline numbers (mean/median/std of generations-to-target, with capped runs either dropped or recorded at the cap) are biased. Use the **fixed-target runtime view counted in function evaluations**. Report **ERT (aRT) = total evaluations over all runs, failed runs included, divided by the number of successful runs**, with the success probability and a bootstrap CI. Add **runtime ECDFs over a ladder of targets** (anytime view), and optionally a fixed-budget view (best f after B evaluations). COCO (`cocopp`) and IOHprofiler (`iohinspector`, IOHanalyzer) both implement this.

### Cited Findings
- **Definition of aRT/ERT in COCO.** The aRT is "computed by summing up all evaluations in unsuccessful algorithm runs as well as the number of evaluations consumed in the successful algorithm runs, both divided by the number of successful runs". Failed runs add their full evaluation count to the numerator; only successes count in the denominator. — [Constrained-benchmarking review, arXiv:1806.04563](https://arxiv.org/pdf/1806.04563); [Hansen et al., COCO: Performance Assessment, arXiv:1605.03560](https://arxiv.org/pdf/1605.03560)
  - Formula: `ERT(f_t) = ( Σ_{i ∈ succ} RT_i + Σ_{j ∈ unsucc} RT_j^{max} ) / #succ`, which equals `E[RT_succ] + (1−p_s)/p_s · E[RT_unsucc]` for independent restarts. — same sources
- **Why the formula looks this way.** For a run that never hits the target, "this runtime remains undefined — while it has been bounded from below by the number of evaluations in this unsuccessful run" ([COCO platform paper, arXiv:1603.08785](https://arxiv.org/pdf/1603.08785)). COCO models a conceptual restart algorithm. The number of failed runs before the first success follows a negative binomial distribution, and "independent restarts of the algorithm solve the problem with probability one". — [arXiv:1605.03560](https://arxiv.org/pdf/1605.03560)
- **Journal version.** Hansen, Auger, Brockhoff, Tušar, "Anytime Performance Assessment in Blackbox Optimization Benchmarking", *IEEE TEVC* 26(6):1293–1305, 2022, DOI 10.1109/TEVC.2022.3210897. It argues for runtime (number of black-box evaluations to reach a target) as the primary measure, aggregated through simulated restarts, averages and ECDFs. — [HAL hal-03814997](https://hal.ip-paris.fr/hal-03814997v2); [IP Paris research portal](https://researchportal.ip-paris.fr/en/publications/anytime-performance-assessment-in-blackbox-optimization-benchmark/)
- **The ECDF is less dependent on reference algorithms than aRT tables.** — [arXiv:1806.04563](https://arxiv.org/pdf/1806.04563) (search summary)
- **Code: `cocopp.toolsstats.sp(data, maxvalue=np.inf, issuccessful=None)`** returns `(SP, success_rate, n_successes)`. Its docstring reads "sum of the function evaluations over all runs divided by the number of success, the so-called success performance which estimates the expected runtime ERT". If no run succeeds it returns `inf`. The source also notes a bug fixed in July 2025, where sorting broke success-rate counting when NaNs were present, so **use cocopp ≥ 2.7.x/2.8**. — [cocopp 2.9.1 on PyPI](https://pypi.org/project/cocopp/) (file `cocopp/toolsstats.py`), [source repo](https://github.com/numbbo/coco-postprocess)
- **Simulated restarts / bootstrap in cocopp.** `drawSP(runlengths_succ, runlengths_unsucc, percentiles, samplesize)`: "A single successful running length is computed by adding uniformly randomly chosen running lengths until the first time a successful one is chosen". The docstring marks it deprecated in favour of `DataSet.evals_with_simulated_restarts`. The default bootstrap sample size is `30 + 970` (= 1000) runs. — cocopp 2.9.1 `toolsstats.py`, `genericsettings.py` ([PyPI](https://pypi.org/project/cocopp/))
- **COCO's target ladder.** cocopp's settings carry `summarized_target_function_values = tuple(10**np.r_[-8:2:0.2])`, i.e. 51 log-spaced targets from 1e2 to 1e-8 (commented in 2.9.1 as one of the target sets). — cocopp 2.9.1 `genericsettings.py` ([PyPI](https://pypi.org/project/cocopp/))
- **IOHanalyzer.** Wang, Vermetten, Ye, Doerr, Bäck, "IOHanalyzer: Detailed Performance Analyses for Iterative Optimization Heuristics", *ACM TELO* 2(1), Art. 3, April 2022, DOI 10.1145/3510426. It focuses on fixed-target running times and fixed-budget performance, aggregates over problems through ECDFs, and reads COCO, Nevergrad, SOS and IOHexperimenter data. — [arXiv:2007.03953](https://arxiv.org/pdf/2007.03953); [HAL](https://hal.archives-ouvertes.fr/hal-03520666)
- **IOHinspector (the Python port of IOHanalyzer)** "aim[s] to achieve feature parity with the IOHanalyzer web-version". It uses polars, reads IOHexperimenter folder structure, and provides "standard fixed-budget and fixed-target plots, EAF and ECDF visualization". It is still flagged "work-in-progress… call signatures changed". — [iohinspector 0.0.8 on PyPI (Aug 2026)](https://pypi.org/project/iohinspector/); [GitHub](https://github.com/IOHprofiler/iohinspector)
- **IOHinspector's ERT code** (`iohinspector.metrics.aggregate_running_time`) aligns runs on 50 log-spaced f-targets. It computes `mean, min, max, median, std, success_ratio, success_count`, plus
  `ERT = Σ_i (RT_i if success else eval_max) / #success` and `PAR-10 = Σ_i (RT_i if success else 10·eval_max) / n`.
  Here `eval_max` defaults to the maximum evaluation count in the data, i.e. the budget. That matches COCO's formula when every failed run uses the full budget, which holds for the SLUD setup with its fixed 500-generation cap. — iohinspector 0.0.8 source ([PyPI](https://pypi.org/project/iohinspector/))
- Other IOHinspector entry points (signatures from 0.0.8): `get_data_ecdf(data, fval_var, eval_var, free_vars, f_min, f_max, scale_f_log, eval_values, …)` and `plot_ecdf`, `fixed_budget`/`plot_single_function_fixed_budget`, `fixed_target`/`plot_single_function_fixed_target`, `get_aocc` (area over the convergence curve, an anytime scalar), `get_tournament_ratings`, `get_robustrank_over_time`, and EAF functions (`get_eaf_data`, `plot_eaf_single_objective`). — iohinspector 0.0.8 ([PyPI](https://pypi.org/project/iohinspector/))
- **Bartz-Beielstein et al. 2020 on aggregation.** For fixed-budget, the arithmetic mean is common and the median is preferred for robustness. For normalized results the geometric mean is suggested (Fleming & Wallace). Quantiles are more robust than standard deviations for dispersion. For target goals, they discuss how to aggregate runs that do not all reach the target. — [arXiv:2007.03488](https://arxiv.org/abs/2007.03488) (search summary)

### Inferences
- In the SLUD study a run "fails" when it hits 500 generations. That is a **right-censored runtime**. Dropping failures from mean/median makes the method that fails more look faster (survivorship bias). Putting the cap value into the mean understates its runtime. Use ERT (COCO definition), and **always pair it with the success rate p̂_s and its Wilson CI** (`scipy.stats.binomtest(k, n).proportion_ci(method='wilson')`, checked in scipy 1.18.1).
- For a single target, the right-censored runtime distribution can be shown as a Kaplan–Meier ECDF: `scipy.stats.ecdf(scipy.stats.CensoredData(uncensored=rt_succ, right=rt_fail))`. Its `.cdf.evaluate/.quantiles/.confidence_interval` methods are present in scipy 1.18.1. `scipy.stats.logrank` exists to compare two censored runtime distributions (checked locally). This is a statistically principled complement to ERT.
- Multiple targets: the current code stops PSO at `fobjmin` (e.g. 1e-8) through `MinimumFunctionValueTermination`. To produce runtime ECDFs over a target ladder (e.g. 1e2…1e-8), log the best-so-far f per generation (or per evaluation) in a callback, and record the first hitting evaluation for each target. Then the ECDF is (fraction of (run, target) pairs hit) vs evaluations/dimension on a log axis. No new runs are needed if the trace is stored.
- A fixed-budget view (median and IQR of best-so-far f at budgets such as 10·n, 100·n, 1000·n evaluations) is cheap once traces exist, and answers the practitioner question "what quality do I get for a given effort?".

## Q2. Performance profiles (Dolan & Moré 2002) and data profiles (Moré & Wild 2009)

### Takeaway
A **performance profile** shows, for each solver, the fraction of problems on which its cost is within a factor τ of the best solver. A **data profile** shows the fraction of problems solved within a budget of α "simplex gradients", i.e. evaluations/(n_p+1). Both are ECDFs. With only three "solvers" (SLUD/LUD/LIN parametrizations) and a handful of functions, they are useful as one compact cross-function summary figure. They are not a substitute for per-function runtime ECDFs and tests. No mature, maintained dedicated Python package was confirmed. A roughly 15-line NumPy implementation is standard.

### Cited Findings
- **Performance profile (Dolan & Moré, *Math. Programming* 91(2):201–213, 2002).** Ratio `r_{p,s} = t_{p,s} / min_s t_{p,s}` (best solver = 1). Profile `ρ_s(τ) = |{p ∈ P : r_{p,s} ≤ τ}| / n_p`. A failed solver gets `r_{p,s} = r_M` (a large value). — [Argonne preprint P1471 / Moré–Wild](https://www.mcs.anl.gov/uploads/cels/papers/P1471.pdf); [ResearchGate record of Dolan & Moré](https://www.researchgate.net/publication/1853672_Benchmarking_optimization_software_with_performance_profiles); [Beiranvand et al., "Best practices for comparing optimization algorithms", arXiv:1709.08242](https://arxiv.org/pdf/1709.08242)
- **Data profile (Moré & Wild, *SIAM J. Optim.* 20(1), 2009).** `d_s(α) = |{p ∈ P : t_{p,s}/(n_p+1) ≤ α}| / |P|`. Here t_{p,s} is the number of evaluations needed to pass the convergence test, and n_p+1 is "the number of function evaluations required to compute a simplex gradient". Data profiles are CDFs: monotone step functions with values in [0,1]. — [Argonne P1471](https://www.mcs.anl.gov/uploads/cels/papers/P1471.pdf); [arXiv:1711.09407](https://arxiv.org/html/1711.09407)
- **Contrast.** Performance profiles compare solvers relative to each other. Data profiles score each solver against a fixed budget, independent of the others. — [arXiv:1711.09407](https://arxiv.org/html/1711.09407)
- Beiranvand, Hare & Lucet's "Best practices for comparing optimization algorithms" (*Optim. Eng.* 2017) surveys performance profiles, data profiles and accuracy profiles as standard reporting tools. — [arXiv:1709.08242](https://arxiv.org/pdf/1709.08242)
- COCO's runtime ECDFs aggregated over functions, with x = evaluations/dimension, are conceptually a data profile with multiple targets per problem and simulated restarts. — [arXiv:1605.03560](https://arxiv.org/pdf/1605.03560) (COCO describes ECDF aggregation of runtimes across problems and targets; the equivalence is my reading)

### Inferences
- For a stochastic optimizer, define t_{p,s} as **ERT** (or median runtime with failures set to ∞) on problem p. A "problem" can be (function × dimension × target). Use **evals/(n+1)** on the x-axis of a data profile. This matters for SLUD because **LUD doubles the number of decision variables** (see the project code `SignedUniLogMANYRUNS.py`: "if using LUD, the number of variables is doubled"). Per-dimension normalization is therefore needed to compare the parametrizations fairly, and the dimensional cost of LUD should be stated explicitly.
- Known caveat (Gould & Scott 2016, "A note on performance profiles"): with more than two solvers, a performance profile does not give a valid ranking beyond the best. The curves for non-best solvers depend on which other solvers are included. This is the same "depends on the other competitors" issue as mean-rank post-hoc tests (Q3). Not verified in this session; see Gaps.
- Python: write it directly. The recipe below was checked to run:
  ```python
  T = ert_table.unstack()            # rows = problems, cols = SLUD/LUD/LIN (np.inf if no success)
  R = T.div(T.min(axis=1), axis=0)   # performance ratios
  taus = np.logspace(0, 2, 200)
  perf_prof = {s: [(R[s] <= t).mean() for t in taus] for s in R}
  ```

## Q3. Hypothesis testing, effect sizes, multiple comparisons, Bayesian alternatives; what guideline papers recommend

### Takeaway
State of the practice in EC journals (2026): (1) **per function**, a two-sample rank test on the runtime or final-quality samples (Mann–Whitney/Wilcoxon rank-sum; signed-rank only if runs are truly paired), with an **effect size (Vargha–Delaney Â12 or Cliff's δ = 2·Â12−1)** and **Holm** (FWER) or BH (FDR) correction across all tests. (2) **Across functions**, an omnibus Friedman test on per-function summaries, with **pairwise Wilcoxon signed-rank + Holm** preferred over Nemenyi mean-rank post-hoc tests (Benavoli et al. 2016), and a critical-difference (CD) diagram as the display. (3) **Bootstrap CIs** on ERT, medians and success rates. (4) Optionally a **Bayesian** analysis (Bayesian signed-rank with a ROPE, `baycomp`/`autorank`; Bayesian Plackett–Luce ranking à la Calvo et al.) reporting P(A better), P(practically equivalent), P(B better). With only 3 parametrizations and a few functions, the Friedman/CD machinery has little power. Per-function tests with effect sizes plus an across-function signed-rank or Bayesian test are more informative.

### Cited Findings
- **Benavoli, Corani & Mangili, "Should We Really Use Post-Hoc Tests Based on Mean-Ranks?", JMLR 17(5):1–10, 2016.** The mean-ranks post-hoc test (Nemenyi after Friedman) is internally inconsistent: whether a pair differs "depends on which other algorithms were in the experiment". They recommend pairwise tests whose outcome depends only on the two algorithms, such as the sign test or **Wilcoxon signed-rank with family-wise error control**, or Bayesian methods. — [JMLR v17 benavoli16a](https://www.jmlr.org/papers/v17/benavoli16a.html); [arXiv:1505.02288](https://ar5iv.arxiv.org/html/1505.02288)
- **Benavoli, Corani, Demšar & Zaffalon, "Time for a Change: a Tutorial for Comparing Multiple Classifiers Through Bayesian Analysis", JMLR 18(77):1–36, 2017.** They argue NHST "should be abandoned". They develop a **Bayesian signed-rank test** whose posterior over (left, ROPE, right) is plotted on a simplex. The **region of practical equivalence (ROPE)** lets one conclude practical equivalence, and adding a ROPE can change conclusions. — [JMLR v18 16-305](https://jmlr.org/papers/v18/16-305.html); [arXiv:1606.04316](https://arxiv.org/pdf/1606.04316)
- **Calvo, Shir, Ceberio, Doerr, Wang, Bäck, Lozano, "Bayesian performance analysis for black-box optimization benchmarking", GECCO 2019 Companion, pp. 1789–1797, DOI 10.1145/3319619.3326888.** "The most commonly used statistics in EC are of the Wilcoxon-Mann-Whitney-test type, and using such statistics… has several known drawbacks". They apply Bayesian inference to 11 EAs on 23 discrete problems (IOHprofiler data), compute each algorithm's **probability of winning**, discuss priors and sample sizing, and give p-value tests as reference. — [HAL hal-02179609](https://hal.sorbonne-universite.fr/hal-02179609); [EHU record](https://ekoizpen-zientifikoa.ehu.eus/documentos/5ee5569429995234a5df109d?lang=en)
- **Corani et al. 2017, "Statistical comparison of classifiers through Bayesian hierarchical modelling", *Machine Learning*.** This is the hierarchical model implemented as `baycomp.HierarchicalTest`, which takes 2-D arrays (rows = data sets/problems, columns = repeated runs). — baycomp 1.0.3 docstring ([PyPI](https://pypi.org/project/baycomp/)); [paper PDF link in docstring](http://repository.supsi.ch/7416/1/hierarchical.pdf)

### Inferences
- **Pairing in SLUD runs.** The project reuses `seed = iteration` for each distribution, and pymoo 0.6.2 creates `np.random.default_rng(seed)` per algorithm (verified in `pymoo/core/algorithm.py`). Runs with the same seed under SLUD/LUD/LIN therefore share the PSO random stream (common random numbers). Because the parametrizations and even the dimension (LUD doubles n) differ, the streams decouple quickly, and the pairing carries little information. **The defensible within-function test is the unpaired Mann–Whitney U / rank-sum** (or Brunner–Munzel if spreads differ). Signed-rank should be reserved for **across-function** comparisons, where the block is the function (or function × dimension).
- **Censoring and rank tests.** Rank tests handle censored runtimes naturally if every failed run is assigned a value worse than any success (e.g. +∞ or 10× budget, i.e. PAR-10). Ties among failures are handled by midranks. Do not drop failures. Alternatively use the log-rank test on the Kaplan–Meier curves.
- **Â12 direction.** With minimization of runtime, `Â12(x, y) = P(X < Y) + 0.5·P(X = Y)` = `mannwhitneyu(y, x).statistic / (len(x)*len(y))`. Â12 > 0.5 means x (e.g. SLUD) is faster. This was checked on synthetic data. Report Cliff's δ = 2Â12 − 1 if reviewers expect it.
- **Multiplicity.** Count every test you report (functions × pairs × targets). With 4 functions × 2 pairs (SLUD vs LUD, SLUD vs LIN) that is 8 tests. Holm is uniformly more powerful than Bonferroni and still controls FWER.
- **Nemenyi CD formula** (Demšar 2006, standard background, not fetched in this session): `CD = q_α · sqrt(k(k+1)/(6N))`, with k algorithms and N problems. With k = 3 and N = 4–8 functions, the CD is large and Friedman/Nemenyi will rarely be significant. That is one more reason to emphasise per-function effect sizes and an across-function Wilcoxon signed-rank/Bayesian signed-rank on per-function ERT ratios.
- **Bootstrap.** Use `scipy.stats.bootstrap(..., paired=True, vectorized=False, method='percentile' or 'BCa')` with a statistic that computes ERT from `(evals, success)` arrays (recipe in Q6). Resample runs. This CI also covers the uncertainty in p̂_s.
- **Bayesian option** for a journal paper in 2026: `baycomp.two_on_multiple(ert_slud_per_fn, ert_lud_per_fn, rope=…)` on log-ERT across functions, or `baycomp.HierarchicalTest` on (functions × runs) arrays. The ROPE must be justified in domain terms, e.g. "ERT within ±5% is practically equivalent" means rope = log(1.05) on log-ERT.

## Q4. Counting function evaluations vs generations vs wall-clock

### Takeaway
**Count objective-function evaluations.** That is the black-box cost model used by COCO, IOHprofiler and the Moré–Wild data profiles. Generations are acceptable only as a derived quantity when population size is fixed and identical across compared methods, and evaluations = pop_size × generations (+ initial population) should be reported. Wall-clock time is machine-, implementation- and load-dependent. It should be reported only as a secondary, clearly specified measurement, e.g. CPU model, single thread, pyperf-style repeated timing.

### Cited Findings
- COCO's runtime is the number of black-box evaluations needed to reach a target. Hansen et al. argue that runtime measured this way is the main performance measure. — [IP Paris record of TEVC 2022 paper](https://researchportal.ip-paris.fr/en/publications/anytime-performance-assessment-in-blackbox-optimization-benchmark/); [arXiv:1605.03560](https://arxiv.org/pdf/1605.03560)
- Moré & Wild measure cost in **function evaluations normalized by n_p+1** (the cost of one simplex gradient), making budgets comparable across dimensions. — [Argonne P1471](https://www.mcs.anl.gov/uploads/cels/papers/P1471.pdf)
- IOHanalyzer's fixed-target and fixed-budget analyses are indexed by evaluation counts (`evaluations` is the default `eval_var` in IOHinspector). — [arXiv:2007.03953](https://arxiv.org/pdf/2007.03953); iohinspector 0.0.8 source ([PyPI](https://pypi.org/project/iohinspector/))
- pymoo's PSO default `pop_size=25`. The SLUD code uses `n_pop = 100`, `n_gen = 500`, and terminates on `TerminateIfAny(n_gen, MinimumFunctionValueTermination(fobjmin))`. — pymoo 0.6.2 `algorithms/soo/nonconvex/pso.py` ([PyPI](https://pypi.org/project/pymoo/)); project file `SignedUniLogMANYRUNS.py`
- `pyperf` 2.10.0 is the PSF tool for rigorous wall-clock benchmarking (calibration, multiple processes, outlier-robust stats), if timing must be reported. — [pyperf on PyPI](https://pypi.org/project/pyperf/)

### Inferences
- For SLUD, generations × 100 = evaluations (plus 100 for initialization), so converting is trivial. Report runtimes in **evaluations** and **evaluations/dimension**, because LUD changes the dimension. Use `res.algorithm.evaluator.n_eval` from pymoo rather than inferring from `n_gen`.
- The parametrization (SLUD transform) may have a different per-evaluation CPU cost. If that matters to the claim, report it separately (µs per transform) rather than mixing it into runtime.
- Termination granularity: pymoo checks the f-target once per generation, so the first-hitting time is only known to within one generation (100 evaluations). Logging per-evaluation best-so-far (e.g. wrapping the problem's `_evaluate`) gives exact first-hitting evaluations, which is what COCO/IOH record.

### Gaps
- I did not retrieve a guideline passage that explicitly forbids generations as the unit. The recommendation follows from COCO/IOH/Moré–Wild practice.

## Q5. Reproducibility: seeding, environment capture, data/code sharing, artifact badges, journal policies

### Takeaway
Minimum 2026 standard for an EC journal paper: (1) a **single root `SeedSequence` entropy recorded in the paper and repository**, with per-run child seeds via `spawn` (or `SeedSequence(root, spawn_key=(run_id,))`) passed to pymoo as integers, and **all** runs reported, never selected. (2) An exact environment: `pyproject.toml` plus a **lockfile** (uv.lock / pip-tools / conda-lock), Python and library versions, OS/CPU, ideally a container. (3) **Raw per-run data** (traces, not just summaries) in an open format (Parquet/CSV or the IOHexperimenter format) archived with a **Zenodo DOI**, plus code archived (GitHub release → Zenodo DOI, or Software Heritage). (4) A one-command script that regenerates every table and figure. (5) Optionally an ACM-style artifact badge / RCR report.

### Inferences
- **Seeding recipe for SLUD.** The current code uses `seed = iteration` (0, 1, 2, …). That is reproducible but is a "hand-picked-looking" scheme, and it gives correlated low-entropy seeds across experiments. Prefer:
  ```python
  ROOT = 0x5_1D_2026  # publish this number (or log SeedSequence().entropy)
  def run_seed(func_id, dist_id, run_id):
      ss = np.random.SeedSequence(ROOT, spawn_key=(func_id, dist_id, run_id))
      return int(ss.generate_state(1, dtype=np.uint32)[0])   # pymoo takes an int seed
  ```
  Deterministic `spawn_key`s give the same seed for a given (function, distribution, run) regardless of worker scheduling in `concurrent.futures`/`joblib`. Store the seed in every result row. Decide deliberately whether distributions share seeds (common random numbers) and say so in the paper.
- **Run count.** The local `SignedUniLogMANYRUNS.py` loops `range(1000)` (and only over `'brown'`), while the paper reports 200 runs. Reviewers will expect the archived code to reproduce exactly the reported N. Make N a config parameter and record it in the output metadata.
- **Environment.** Check in `pyproject.toml` and `uv.lock` (or `requirements.txt` from `pip-compile --generate-hashes`). Write `sys.version`, `numpy.__version__`, `pymoo.__version__`, platform and git commit hash into each results file's metadata. pymoo internals (PSO update rules, defaults) change between minor versions, so pin `pymoo==0.6.2` (or whatever is used).
- **Data.** Store one long-format table: one row per (function, dimension, distribution, run, evaluation-at-improvement) with columns `best_f`, `seed`, `success`, `n_eval`. Write it as Parquet (pandas/polars) and archive it on Zenodo with the code release (GitHub–Zenodo integration gives a DOI per release). Optionally also export in IOHexperimenter format so IOHanalyzer/IOHinspector can load it directly. That is a recognized format and lets reviewers re-plot.
- **Artifact evaluation.** If targeting ACM TELO, an RCR/badge submission is feasible for a small Python code base. The "Functional" badge needs a README with exact commands, expected runtime, and expected outputs within stated tolerance (stochastic results must reproduce bit-for-bit with the published seeds on the same library versions, or within CI otherwise).

## Q7. Common pitfalls reviewers flag

### Takeaway
For SLUD, the most likely reviewer objections are: **too few and too easy test functions** (Rosenbrock, Brown, Powell, a polynomial; no rotated/shifted standard suite, no dimension scaling); **dropping or capping failed runs** (budget-cap bias); **reporting means only** without dispersion, CIs or effect sizes; **only one optimizer (PSO) with default parameters**, so it is unclear whether the effect is PSO-specific; **generations instead of evaluations**, with an unequal dimension for LUD; **no multiple-testing correction**; and **no shared code or data**.

### Cited Findings
- EC comparisons mostly use Wilcoxon–Mann–Whitney-type statistics "with several known drawbacks" when used alone for performance comparison. — [Calvo et al. GECCO 2019, HAL](https://hal.sorbonne-universite.fr/hal-02179609)
- Mean-rank post-hoc results depend on the set of competitors included. — [Benavoli et al. JMLR 2016](https://www.jmlr.org/papers/v17/benavoli16a.html)
- Failed runs have undefined runtime, bounded below by their evaluations, and must enter the ERT numerator, not be discarded. — [arXiv:1603.08785](https://arxiv.org/pdf/1603.08785); [arXiv:1806.04563](https://arxiv.org/pdf/1806.04563)
- Bartz-Beielstein et al. call for clearly stated goals, well-specified problems, adequate measures and robust dispersion statistics (quantiles over SD). — [arXiv:2007.03488](https://arxiv.org/abs/2007.03488)
- Number of instances, not just runs, drives statistical power for class-level claims, and there is "no established rule" for choosing either. — [Campelo & Takahashi, arXiv:1808.02997](https://arxiv.org/pdf/1808.02997)
- About 63% of GECCO ECOM papers over ten years provide no material beyond the manuscript, with average checklist completeness 0.62. Missing artifacts are a widespread, now-measured problem. — [arXiv:2602.07059](https://arxiv.org/html/2602.07059v1)
- LaTorre et al. 2021 was written to help "reviewers and editors along their assessment of new contributions", so its checklist is likely what reviewers apply in *Swarm and Evolutionary Computation*. — [arXiv:2004.09969](https://arxiv.org/pdf/2004.09969)

### Inferences
- **Function set.** Add a standard suite. COCO `bbob` (24 functions, dims 2–40, instances), via `cocoex` or `ioh` which also exposes BBOB, makes results comparable and lets you report runtime ECDFs aggregated over function groups. SLUD's niche is variables spanning many decades. Also include custom problems whose optimum lies at very small/large magnitudes and mixed signs, and vary where the optimum sits in the decades (several instances), so the benefit is not an artifact of one optimum location.
- **Optimizer generality.** Repeat with at least one other optimizer (pymoo GA/DE, or CMA-ES via `cma`/`pycma`) to show that the parametrization effect is not PSO-specific. Tune or at least justify PSO parameters equally for all parametrizations. Do not tune on the reporting functions.
- **Budget-cap bias.** 500 generations is arbitrary. Show that conclusions are stable at a larger cap, or report ERT plus success rate so that the cap's effect is visible. Show ECDFs up to the cap.
- **Cherry-picking.** Pre-specify functions, targets, N and the seed scheme in the repository before running (a short `PREREGISTRATION.md` or config). Report all runs. Never select seeds.
- **Dimensionality.** Report results for several n (e.g. 2, 5, 10, 20). A "spans many decades" benefit could change with n, and LUD's 2n variables is a confound that must be discussed.
- **Means only.** Show distributions: ECDFs, box/violin plots on a log scale, medians with bootstrap CIs, success rates with Wilson CIs.

### Gaps
- I found no source that quantifies how often reviewers raise each pitfall. The list is synthesized from the guideline literature cited above.

## Q8. Concrete analysis-section checklist for the SLUD paper (synthesis)

### Takeaway

### Cited Findings

9. **Across-function test**: Wilcoxon signed-rank on per-function log-ERT (or median) differences, with Holm across pairs. Show a CD diagram (`scikit_posthocs.critical_difference_diagram` with a Wilcoxon-Holm sig matrix, or `autorank.plot_stats`). Acknowledge low power with few functions.
